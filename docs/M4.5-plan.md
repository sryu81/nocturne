# M4.5 — Real on-device frame storage (Preview/Plan split) + offline coarse plate solver

## Context

Two things raised together this session, bundled into one doc since the second consumes the
first: (A) M4.3 shipped Room-backed frame persistence, but JPEG bytes live only in SQLite's own
blob column — no real files ever land on the phone's storage, and nothing distinguishes a bench
"Preview" test shot from a real scheduler-job capture. User specified real folder templates for
both. (B) A genuinely new capability: an **offline** coarse plate solver running entirely on the
phone, for a framing check when not connected to the rig at all — explicitly wide-field/coarse
scope, not a narrow-field astrometry.net-grade solve.

## Part A — Real on-device frame storage

### Current state (M4.3, already shipped)

`FrameEntity` stores `jpeg: ByteArray` straight in Room's SQLite blob column. No folder
structure, no on-disk files, no test-vs-target distinction — every real capture frame lands in
one flat table.

**Real constraint, confirmed against source (M4-plan.md)**: the Media-channel header itself
carries no target name, filter, or frame type — `MediaHeader`'s confirmed real fields are purely
imaging metadata (`exposure`/`gain`/`bin`/`focal_length`/`pixel_size`/`hfr`/stats/`resolution`/
`uuid`/...). The **only** way to know "this frame is a test shot" vs "this frame belongs to
target X, filter Y" is to check what's active in `AppState` at the exact moment the frame
arrives (`schedulerRunning` + the `BUSY` entry in `wireSchedulerJobs`, or fall back to a plain
"no active job → test" default). This is a real, load-bearing assumption, not a guaranteed
correlation — flagged here explicitly rather than presented as solid, same discipline as every
other "fragile but no better wire signal exists" case in this codebase.

### Real folder templates (user-specified 2026-08-23)

**Preview/test captures** (Bench "Preview Main Cam"/"Preview Guide Cam", `JOBTYPE_PREVIEW` on the
real side — confirmed via `cameraprocess.cpp`, a genuinely different job type from a scheduler
job):
```
Preview/<session-datetime>/Prev_00000.jpg
Preview/<session-datetime>/Prev_00001.jpg
...
```
Assumption (not yet confirmed with you — cheap to change): one dated folder per app session
(created the first time a preview frame lands after connect), counter zero-padded to 5 digits,
reset to 0 for each new session folder.

**Scheduler/target captures**:
```
Plan/%D/%t/%t_%D_%F_%Esec_%CC_%s1.jpg
```
Tag meanings (confirmed with you):
- `%D` — capture date. Assumption: `yyyy-MM-dd` (flag if you want a different format).
- `%t` — real target name, from the active scheduler job at arrival time.
- `%F` — real filter name. **Not available from the Media header** — must come from
  `wireCaptureSettings?.FilterPosCombo` (the real live Capture-tab filter, already wired) at the
  moment the frame lands. Same correlation caveat as above.
- `%E` + literal `sec` — real exposure value from the frame's own header (`MediaHeader.exposure`,
  already real), e.g. `300sec`.
- `%C` + literal `C` — real sensor temperature, e.g. `-10C`. **Not from the Media header** (no
  temperature field there) and **not from `new_camera_state`** (decoded but deliberately a no-op
  per M4.4 — `CoolerCard` already reads the real, more precise `CCD_TEMPERATURE` INDI number
  directly). This needs the same live INDI read (`state.indiNumber(camera, "CCD_TEMPERATURE")`)
  at frame-arrival time.
- `%s` + `1` — per-frame sequence number, 1-indexed, scoped to this exact target+filter+exposure
  combination (confirmed with you). Assumption: no zero-padding (flag if you want e.g. `%03d`).

Real full example: `Plan/2026-08-23/NGC7000/NGC7000_2026-08-23_Ha_300sec_-10C_1.jpg`.

### Implementation

- New `FrameFileWriter` (in `data/FrameDatabase.kt` or a new `data/FrameFileWriter.kt`): given a
  real `MediaFrame` plus capture context (test vs. real target/filter/temperature), writes the
  JPEG to `context.getExternalFilesDir(null)` (app-scoped storage, no runtime permission needed
  on modern Android) under the `Preview/`/`Plan/` structure above, returns the real file path.
- `FrameEntity` gains `filePath: String` (the real on-disk path) — the JPEG moves from a Room
  blob column to a real file; Room just indexes metadata + path, so the SQLite file itself stays
  small and the grid's thumbnails read `File(filePath).readBytes()` instead of `entity.jpeg`.
  (`MediaFramePreview`'s `ByteArray?` overload stays the same — just fed from a file read now.)
- `EkosRemoteController`'s capture-frame routing (M4.1, `client.mediaFrames.collect`) gains the
  real "what's active right now" lookup described above, to pick Preview-vs-Plan and fill in the
  real tag values before handing off to `FrameFileWriter`.

### Verification

Live, real rig: tap Preview Main Cam, confirm a real file lands at
`Preview/<date>/Prev_00000.jpg` on the phone's own storage (`adb shell` or a file browser); push
+ start a real scheduler job, confirm captures land under `Plan/<date>/<target>/...` with the
real filter/exposure/temperature substituted correctly, and confirm the per-target+filter
sequence counter (`%s1`, `%s2`, ...) increments correctly across multiple subs.

## Part B — Offline coarse plate solver (framing check only)

### Scope, per your call

Offline only — no dependency on the rig or the real `align_solve`. Wide-field, coarse accuracy —
a small bundled bright-star catalog, explicitly not narrow-field-capable.

### Real shortcut this scope gets for free

`MediaHeader` already carries real `focal_length`/`pixel_size`/`bin` — plate **scale**
(arcsec/pixel) is analytically known, not something the solver needs to search for:

```
scale_arcsec_per_px = 206265 * pixel_size_µm * binning / (focal_length_mm * 1000)
```

This cuts a general "lost in space" solve's 4 unknowns (RA, Dec, rotation, scale) down to 3 (RA,
Dec, rotation) — a meaningfully smaller, phone-appropriate search.

### Approach

1. **Star extraction** — threshold + connected-component centroid detection directly on the
   already-decoded bitmap (`MediaFramePreview` already does the JPEG→`ImageBitmap` decode; reuse
   that path). Pure image processing, no astrometry involved at this step.
2. **Bundled catalog** — ~5000 brightest stars (Yale Bright Star Catalog / a Hipparcos subset,
   real RA/Dec/magnitude), packed as a small binary asset (low hundreds of KB — not
   astrometry.net's own 100MB+ index files, appropriate for the wide-field-only scope actually
   agreed here).
3. **Geometric-hash matching** — same family as astrometry.net/Tetra's asterism approach,
   simplified: build invariant features (pairwise distance ratios/angles) from the observed
   centroids and from catalog subsets, matched using the known real scale from above to prune
   candidates before any expensive matching.
4. **Fit** — once ≥3–4 stars match, fit a similarity transform (RA/Dec center + rotation) from
   image-pixel coordinates to catalog RA/Dec.
5. **Output** — frame-center RA/Dec + rotation angle, shown on a new "Solve" action on the frame
   overlay (`SubPreviewOverlay` for a live frame, `FrameExpandOverlay` for a saved one).

### Honest accuracy expectations (told to you up front, not overpromised)

- Coarse framing confirmation only — "am I pointed at the right nebula," not sub-arcsecond
  precision comparable to real astrometry.net/ASTAP.
- Needs enough bright stars in the actual frame (roughly naked-eye-visible, magnitude ≲6) — a
  narrow deep-sky frame with few bright stars may simply fail to solve. That's the expected
  behavior of this scope, not a bug to chase.
- Does **not** feed back into real Ekos/Align at all — a purely local, informational overlay in
  Nocturne, independent of the rig.

### Open items needing a decision before implementation starts

- Exact catalog source + how it gets parsed into the bundled binary asset (Yale BSC5 is public
  domain; still needs real sourcing/parsing work, not assumed done).
- Real on-device runtime budget (star extraction + matching cost) — can't be estimated from
  source reading alone; needs a first working pass actually measured on the phone.
- Confirm the UI entry point (`SubPreviewOverlay`/`FrameExpandOverlay` "Solve" button, as
  proposed above) before wiring it in.
